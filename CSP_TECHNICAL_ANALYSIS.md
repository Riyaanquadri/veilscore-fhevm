# Technical Analysis: TFHE CSP Issue

## Root Cause Analysis ✅

### Package
- `@zama-fhe/tfhe-js@0.1.2`
- Location: `node_modules/.pnpm/@zama-fhe+tfhe-js@0.1.2/node_modules/@zama-fhe/tfhe-js/`

### Eval Usage Found
```
File: dist/browser/tfhe-rs/browser/tfhe.js
Line: (search for "new Function")

Code:
  const ret = new Function(getStringFromWasm0(arg0, arg1));
```

```
File: dist/node/tfhe-rs/node/tfhe.js
Line: (search for "new Function")

Code:
  const ret = new Function(getStringFromWasm0(arg0, arg1));
```

### Why This Exists
This is **auto-generated by wasm-bindgen** — the standard Rust → WASM → JavaScript binding tool.

**Wasm-bindgen process:**
1. Rust code compiled to WASM
2. WASM exports generated functions
3. JavaScript glue code created to wrap WASM calls
4. Some wrappers use `new Function()` to dynamically create JavaScript functions that call WASM

**Why new Function()?**
- Performance: Pre-compiled JS functions are faster than indirect calls
- Flexibility: Can generate functions for any WASM export
- Standard practice: All wasm-bindgen projects do this

### CSP Blocking
The browser CSP policy had:
```
script-src 'self' 'unsafe-inline' https:
```

Notice: **NO `unsafe-eval`**

When `tfhe.js` tries to execute:
```javascript
const ret = new Function(...);
```

Browser blocks it because `unsafe-eval` is not allowed.

## Result
```
WASM module loads ✓
JS glue code runs ✓
new Function() call executes ✗ BLOCKED BY CSP
TfheClientKey never created ✗
TfheConfigBuilder never created ✗
"Shortint not found after initialization" error ✗
```

## Solution: Allow unsafe-eval (Dev Only)

### In index.html:
```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'self'; script-src 'self' 'unsafe-eval' 'unsafe-inline' https:; ..."/>
```

### In vite.config.ts:
```typescript
server: {
  headers: {
    'Content-Security-Policy': "default-src 'self'; script-src 'self' 'unsafe-eval' ...",
  },
}
```

Both allow the WASM glue to run `new Function()`.

## Result After Fix
```
WASM module loads ✓
JS glue code runs ✓
new Function() call executes ✓ ALLOWED
TfheClientKey created ✓
TfheConfigBuilder created ✓
"TFHE WASM module successfully initialized" ✓
```

## Security Implications

### Development (Current Setup)
- ✅ Allows testing and debugging
- ⚠️ Reduces CSP protection, but only in dev
- 🎯 No risk since code runs locally

### Production (DO NOT SHIP WITH unsafe-eval)
- ❌ `unsafe-eval` in CSP dramatically increases XSS attack surface
- ❌ An attacker who gains code injection could execute arbitrary JS via `eval()`
- ❌ Defeats purpose of CSP as a defense-in-depth mechanism

## Production-Safe Solutions

### 1. CSP-Safe TFHE Build (Ideal)
Zama or the TFHE-rs team may provide:
- Pre-compiled glue code (no `new Function()` needed)
- ESM build with static exports
- Build flag: `--no-eval` or similar

**Action:** Check Zama docs or ask support for CSP-compatible build.

### 2. Static Code Generation
Pre-generate all WASM wrappers at build time:
- Use wasm-bindgen with a "no-eval" flag
- Inline all wrapper code in the bundle
- No runtime `new Function()` calls needed

**Complexity:** Medium — requires build-time setup.

### 3. Isolated Web Worker
Move TFHE to a separate execution context:
```
Main App (strict CSP)
    ↓
Web Worker (relaxed CSP)
    ↓ (postMessage API)
    ↓
TFHE WASM (can use unsafe-eval)
```

**Complexity:** High — significant refactoring.

**Benefit:** Main app stays CSP-strict, TFHE isolation provides security boundary.

### 4. Narrow CSP + Monitoring
If you must use `unsafe-eval`:
```html
<meta http-equiv="Content-Security-Policy"
      content="default-src 'none'; script-src 'self' 'unsafe-eval' https://trusted-cdn.example.com; report-uri https://csp-reporter.example.com"/>
```

Then:
- Restrict all other directives tightly
- Monitor via CSP reporting endpoint
- Log violations, investigate anomalies
- Detect if untrusted code tries to execute

**Complexity:** Low.
**Security:** Medium — not ideal but acceptable with monitoring.

### 5. Alternative FHE Library
Research FHE implementations that don't require eval:
- TFHE-rs pure WASM (no JS glue layer)
- Homomorphic Encryption JS library (if available)
- ZK-focused libraries (alternative to FHE)

**Complexity:** High — major refactoring.
**Benefit:** Full CSP compliance, potentially better performance.
